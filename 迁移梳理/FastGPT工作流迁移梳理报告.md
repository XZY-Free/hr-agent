## 一、整体架构

这是一个**人力资源 AI 助手**（考勤请假 + 人力咨询复合应用），由 1 个主入口 + 23 份子应用导出组成（按 pluginId 去重后为 20 个独立子应用、合计 **21 个独立应用**；「查询假期余额」「查询年假余额」「获取用户假期权限」3 个应用被重复导出/引用）。
外部系统是**盖亚劳动力管理平台（GaiaWorks WFM）**，所有业务数据（假期余额、排班、员工信息）均来自盖亚 OpenAPI。

## 二、主流程逻辑（主流程-1）

### 2.1 入口预处理
1. 判断用户输入是否以 `_transparent_data_` 开头（渠道注入的表单回填数据）——若是，用代码节点解析出 startDate/endDate/startTime/endTime/reasons 写入全局变量，直接回显。
2. 判断输入是否为空，空则回复"你输入的内容为空"。

### 2.2 核心路由（按优先级）
```
用户输入
 ├─ 1. 转人工判断（问题分类 qwen-plus：转人工意图 / 其他意图）
 │     └─ 转人工意图 → 回复引导语"请您回复'转人工'…"
 │
 ├─ 2. 其他意图 → 代码判断是否"最快捷"路径
 │     ├─ 非快捷 → 子应用「测试-请假意图判断」
 │     │            ├─ 请假意图 → 进入请假路由（见 2.3）
 │     │            ├─ 咨询意图 → 进入请假路由
 │     │            ├─ 取消请假 → 指定回复
 │     │            └─ 其他意图 → 指定回复
 │     └─ 快捷 → typeName 为空判断 + 变量记录 + 代码组装请假单直接提交
 │
 ├─ 3. 子应用「人力AI咨询（新）」→ 包装为 {"businessType":"consult","result":...} 返回
 │
 └─ 4. 子应用「测试-AI助手能力拓展」（页面跳转路由）
```

### 2.3 请假路由（核心决策）
请假意图进入后，由 **AI 路由判断器**（qwen-plus，提示词要求仅输出"快捷路径"或"非快捷路径"）分流：

- **快捷路径** → 「测试-AI考勤-快捷（主AB）」
  - 输入匹配 `今天|今日|明天|明日|后天|后日` → A 线（未来日期请假）
  - 否则 → B 线（昨天/前天，过去日期补登记）
  - A 线再按 今天/明天/后天/大后天/下周 分发到 a1–a5
- **非快捷路径** → 「测试-Al-考勤非快捷（C）」（自由文本请假全流程）

路由后统一经过：
1. 「测试-AI考勤-获取用户假期权限」查该员工可申请假期类型
2. **男女假期权限判断**（产假/有薪产假/无薪产假等性别限制，性别不符直接拒绝）
3. typeCode 异常检查（无权申请则回复"你无权申请该假期"）
4. 通过后由代码节点组装请假单提交，回复 `system_rawResponse`
5. 全程用**变量更新节点**把 typeName/startDate/endDate/startTime/endTime/reasons 记录到全局变量（多轮对话槽位记忆）

## 三、各子应用逻辑要点

### 3.1 测试-请假意图判断（6 节点）
单节点问题分类（qwen-plus），输出四类：**请假意图 / 取消请假 / 咨询意图 / 其他意图**。
提示词含严格优先级规则：一票否决（含疑问词/异常描述/情绪犹豫的输入即使含请假动词也归为咨询意图）、纯时间要素视为快捷请假。→ **迁移时这是一段独立的 NLU 意图识别 prompt，可直接复用。**

### 3.2 快捷请假系列 a1–a5 / B（48–57 节点/个，结构同构）
每个应用的骨架完全一致，**唯一差异是日期偏移量**（a1=0 / a2=+1 / a3=+2 / a4=+3 / a5=用户指定下周某日 / B=-1或-2）：

1. 文本拼接排班表 → 判断是否"提前1小时下班"特例（是则 typeName=调休假）
2. 代码计算目标日期 → 从排班数据提取当天班次
3. 首班时间是否为 00:00 → 判断是否休息日/未排班（有固定话术："正常休息不用请假"/"还未排班"）
4. 写 startDate/endDate/startTime/endTime → 开始>结束则 endDate+1（夜班跨天）
5. 正则匹配"上半/下半/全天" → leaveDays = 0.5 / 1 天
6. 代码查余额校验 → 代码组装请假单提交 → 指定回复

> **迁移建议：7 个应用合并为 1 个工具函数** `process_quick_leave(date_offset, user_input)`，日期解析交给 NLU。

### 3.3 测试-Al-考勤非快捷（C）（126 节点，最复杂）
自由文本请假的完整对话状态机：

1. **入口特判**：今日提前1小时下班特例；正则防止一条消息含多种假期（tag 变量）
2. **一级意图分类**（qwen-max）：错误请假申请（多种假期→"请分开提交"）/ 余额查询（→子应用查询假期余额#4）/ 改换类型 / 请假申请
3. **请假申请主线**：4 个内容提取节点并行抽取四要素（休假类型/日期/时间/理由）→ 合并 JSON → 完整度校验（缺槽→追问话术）
4. **时间精修**：AI 对话识别时间段/调休 → 真实时间提取 → 年份校验 → 跨天修正
5. **排班核算**：子应用「测试-获取排版信息」查排班 → 计算实际天数 leaveDays → 子应用「根据休假类型去判断是否跳过休息日」校正起止日期（见 3.7）
6. **提交**：代码节点（入参六元组 typeName/startDate/endDate/holidayType/reasons/leaveDays）→ 回复，tag 归零
7. **改换类型分支**：二级分类（改日期/类型/理由/时间）→ 提取新值 → 汇合到同一提交点

### 3.4 人力AI咨询（新）（90 节点，知识库核心）
见第四章详细拆解。整体管线：
**名词解释 → 问题改写 → 非人力过滤 → 业务分类 →（咨询知识库 / 地区育儿假 / 考勤计算）→ 专家回答 + 追问生成**

### 3.5 测试-AI助手能力拓展（26 节点）
意图分类（**ali_deepseek-v3.2**，13 类），大多数意图直接返回前端跳转指令：
```json
{"businessType": "page_jump", "permissionCode": "exception"}
```
permissionCode 对照：我的异常=exception、销假申请=request-sick-leave、我的信息=my-info、移动排班=mobile-schedule、打卡明细=punch-details、原始打卡记录=punch-card-records、我的排班=scheduling、考勤统计=attendance-statistics、加班申请=request-overtime、我的表单=my-forms、团队考勤=team-attendance、团队假期余额=leave-quota。
个人假期余额查询 → 子应用「AI考勤-查询假期余额#2」（复用 67e29c66…183c8）。
"其他意图"且代码判断"符合"咨询条件 → **子应用「人力AI咨询（新）」（复用 693a2937…17dc，与主流程下为同一应用，逻辑见 3.4/第四章）**；不符合 → 回复"咨询服务敬请期待"。

### 3.6 考勤工具小应用（统一两段式模式）
查询假期余额 / 获取用户假期权限 / 查询医疗期 / 查询年假余额 / 查询育儿假 / 计算年假天数 / 获取排版信息，全部是同一模式：

```
HTTP 获取盖亚 JWT → 代码解析 JWT（取 data 字段作 Bearer token）
→ 判断成功 → HTTP 调业务接口 → 代码解析响应 → 格式化话术回复
→ 失败/异常 → 构建错误信息回复（均有 catch 异常捕获分支）
```

其中**计算年假天数**额外逻辑：查员工信息 → 解析工龄（参工年限/本单位工龄）→ 按 5 天/10 天档位折算 → 再调查询年假余额子应用 → 输出"X月X日前年休假按N天折算…"。

### 3.7 根据休假类型去判断是否跳过休息日（纯规则计算，无接口/知识库）

被「非快捷（C）」调用，作用是根据假期类型决定**请假起止日期的推算方式**（是否跳过休息日），输出调整后的 startDate/endDate。全部逻辑为代码节点，无 LLM、无 HTTP。

**执行流程：**

1. **天数解析（代码运行#4）**：解析请假时长（"1.5天"→1.5、"X个月"→×30 天）；若无法解析或 **> 27 天** → 返回"否"
2. **分支判断**：
   - **天数 > 27 或不可解析（ELSE）** → **工作日收缩模式（代码运行#3）**：startDate 向后找第一个工作日、endDate 向前找最后一个工作日（把长假申请的起止对齐到工作日）
   - **天数 ≤ 27（IF）** → 记录天数 → 提取/确认休假类型 typeName → 查下方静态映射表：
     - 类型标记为"**否**"（跳过休息日）→ **代码运行#2**：以排班表为准，从 startDate 起跳过休息日（shiftCode 为 OFF / off_day / defaultOFF 开头）逐日数够 N 个工作日，endDate = 最后一个工作日；startDate 不在排班数据内则直接按自然日加 N-1 天
     - 类型标记为"是"或未收录 → **代码运行#5**：连续自然日计算，endDate = startDate + (N-1) 天

**27 类假期"是否连续计算（含休息日）"静态映射表（业务规则核心资产，迁移时完整保留）：**

| 连续计算（是） | 跳过休息日（否） |
|---|---|
| 婚假、产假、病假、育儿假、计划生育假、无薪产假、有薪产假、子女护理假、不定时员工日常休假、产前假、陪产假、出差、公出 | 丧假、产检假、非独生子女护理假、事假、调休假、无薪侍产假、80%病假、调休假(综合工时)、有薪侍产假、年休假、无薪假、路程假、全薪病假、哺乳假 |

（映射表之外的类型返回"没有"，走连续计算分支。）

### 4.3 知识库配置对迁移的参考值
- 混合检索 embeddingWeight 0.45–0.7（主流 0.48）

## 八、输入模态与对话历史配置

### 8.1 文件/图片上传与文档解析
- **主流程-1** 开启了文件上传：`fileSelectConfig = {canSelectFile: true, canSelectImg: true, maxFiles: 10}`（可传文件 + 图片，单次最多 10 个）。
- **人力AI咨询（新）** 内有 2 个 `readFiles` 文档解析节点（「文档解析」「文档解析#2」），文件 URL 经全局变量 `nels2UrE (url)` / `lEEF0RmD (url1)` 由主流程传入（见第六章变量表）；该子应用自身未开启上传 UI（fileSelectConfig 为空）。
- **迁移提示**：文件接收（前端上传 → URL）与文档解析（URL → 文本）在 AgentKit 侧是一条独立链路，需要单独设计（文件存储、解析服务选型、图片是否改走多模态模型）。

### 8.2 语音输入
「人力AI咨询（新）」开启了语音转文字：`whisperConfig = {open: true, autoSend: false, autoTTSResponse: false}`（仅语音输入，无自动发送、无 TTS 播报）。迁移时需决定是否保留该能力，以及 ASR 由谁提供（火山引擎 ASR / 前端宿主自带）。

### 8.3 对话历史窗口（⚠️ 行为等价性关键）
全部 60 个 LLM 类节点（31 个 AI 对话 + 10 个问题分类 + 19 个内容提取）中 **55 个 history=0**——绝大多数模型调用**不带聊天历史**，多轮状态完全靠全局变量槽位（typeName/startDate/tag…）传递。仅 5 个节点带历史：

| 节点 | 所在应用 | 模型 | 历史轮数 |
|------|---------|------|---------|
| 问题改写 | 人力AI咨询（新） | qwen-plus | 3 |
| AI 对话#17 | 人力AI咨询（新） | qwen3.7-max | 3 |
| AI 对话#26 | 人力AI咨询（新） | qwen3.6-plus | 3 |
| AI 对话_用户问题与非人力关键词的语义比较 | 人力AI咨询（新） | qwen-plus | 6 |
| 问题分类#2 | 测试-Al-考勤非快捷（C） | qwen-plus | 6 |

**迁移风险**：AgentKit 这类智能体框架默认在每次模型调用注入完整对话历史；若直接迁移，原 history=0 节点看到的输入分布会改变（提示词都是按"无上下文"写的），意图分类/内容提取行为可能不等价。迁移后需逐节点显式控制上下文：默认不注入历史，仅上表 5 个节点按原轮数注入。

另记录模型参数：有显式温度配置的节点以 temperature=0 为主（10 个），3 个节点 temperature=1，其余走模型默认——prompt 迁移时应连同参数一起搬。

## 九、迁移到火山 AgentKit 的建议

> **总体方向（2026-07-25 业务拍板）：不做 1:1 工作流复刻。**
> - FastGPT 的复杂性大部分来自「固定流程 + 变量/判断节点」的工作流形态——不能让 AI 自主决策，只能靠节点穷举分支；同样的业务逻辑在智能体架构下往往一两句规则即可表达。
> - 目标架构：**单主 Agent（一个主模型）+ 技能/工具集**。把业务规则（假期权限校验、27 类假期跳休映射、盖亚 API 调用、页面跳转码表等）沉淀为工具函数/技能，"下一步做什么"由 AI 自主决策，不写死流程；需要时允许主 Agent 派生子 agent。
> - 因此本报告第二、三章流程梳理的用途是**提取业务规则、判断条件和话术资产**，而非照抄流程图；9.1 的模块收敛表是能力盘点视角，不代表按原流程编排。

### 9.1 应用收敛（21 个独立应用 → 建议 6 个模块）
| FastGPT 现状 | AgentKit 目标 |
|---|---|
| 主流程-1 | 主智能体（路由 + 槽位管理） |
| 请假意图判断 + 快捷 a1–a5/B + 非快捷 C | **请假技能**（NLU 槽位抽取 + 日期解析函数 + 提交工具），7 个同构应用合并为 1 个参数化函数 |
| 人力AI咨询（新） | **咨询技能**（知识库检索 + 回答），接入火山知识库 |
| 查询余额/权限/医疗期/育儿假/排班/员工信息（6 个两段式应用） | **盖亚 API 工具集**（6 个 function tool + 统一 JWT 认证中间件） |
| AI助手能力拓展 | 主智能体的一层意图 + 结构化输出（page_jump JSON） |
| 计算年假天数 | 工具函数（员工信息→工龄→折算规则） |

### 9.2 架构性优化点
1. **用 function-calling 槽位抽取替代"4 个内容提取节点 + 合并 JSON + 重组文本"**：一次调用出 typeName/date/time/reason，缺槽再追问。
2. **全局变量 tag 隐式状态机 → AgentKit 显式会话状态**（申请中/改单中/咨询中）。
3. **JWT 工具内缓存**：现在每次调用都重新 oauth，迁移后按 token 有效期缓存。
4. **消除重复子树**：FastGPT 里同一"记录变量→权限判断→提交"子树被复制了 8+ 份，代码化后是一个函数。
5. **环境统一**：生产/沙箱地址混用需确认（获取权限、排班用的是沙箱 openapi-s）。
6. **规则资产代码化**：27 类假期的"是否跳过休息日"映射表（见 3.7）应落为配置文件/常量表，便于 HR 侧维护。
7. **LLM 上下文策略保持等价**：绝大多数节点 history=0（见 8.3），迁移后不要默认给每次模型调用注入全量对话历史，需逐节点显式配置。

### 9.3 业务确认结论（2026-07-25 已拍板，原"待确认事项"全部闭环）
- ✅ **请假提交**：调用链为「后端 → 智能体」。智能体最终只输出请假单 JSON（即原 `system_rawResponse` 的内容），后端拿到 JSON 后**自行调用盖亚请假接口**完成提交——智能体侧不做提交动作，无漏导出。
- ✅ **知识库**：文档直接上传到 **AgentKit 平台知识库**（部署即在 AgentKit，用平台资源），不自建本地向量库。前置动作不变：仍需按第四章对照表到 FastGPT 后台定位各知识库并导出原始文档，再导入 AgentKit。
- ✅ **渠道注入变量**：沿用现有方式——由后端调用智能体时把 employeeId / corp_id / client_secret / grant_type 作为变量传入。
- ✅ **生产/沙箱混用、tenant 硬编码 `snowbeertest`、grant_type 取值**：先全部按工作流导出的原样实现，后续再统一。
- ✅ **`_transparent_data_` 前缀协议**：该分支是同事为方便观察入参加的调试节点，业务上可忽略；协议暂时保留。
- ✅ **文件/图片**：进入智能体时已是**腾讯云 COS 公共访问链接**，智能体侧无需文件存储，直接按 URL 拉取解析即可（8.1 中"文件存储选型"一项不再需要，仅需解析）。
- ✅ **语音输入**：属前端交互层职责，智能体侧不承接（8.2 移出迁移范围）。

### 9.4 已确认的复用关系（pluginId 比对结论）

## 十、智能体框架选型调研（2026-07-25 联网核实）

### 10.1 三个名词分别是什么
- **AgentKit（火山引擎）**：企业级 AI Agent 开发平台，模块化服务可独立使用：**Runtime**（全托管运行时，官方明确支持**任意框架、任意语言**构建的 Agent 部署）+ Tools + Memory + **Knowledge**（知识库，基于 VikingDB）+ MCP + Gateway/Identity/Observability。控制台 `console.volcengine.com/agentkit`。
- **veADK**（Volcengine Agent Development Kit）：火山官方开源智能体开发框架（Python/Go/Java 三语言，Apache 2.0）。**其底座就是 Google ADK**（`google-adk>=1.32.0` 为核心依赖，含 Google A2A 协议支持），在其上叠加火山生态集成：豆包/方舟模型、VikingDB 知识库与长短期记忆、TOS、观测，配套 `agentkit-sdk-python`（CLI）一键部署到 AgentKit Runtime。原生概念：Agent（model / **sub-Agents** / tools / **skills**）、session state。
- **AgentRun（阿里云产品，非火山）**：阿里云的 Serverless 智能体运行时（函数计算体系，Serverless-Devs 工具链部署，OpenAI 协议入口）。官方集成扩展：AgentScope、LangChain、**Google ADK**、CrewAI、PydanticAI，同样声明"可使用任意框架开发"。

### 10.2 「AgentKit 与 AgentRun 共同支持的框架」结论
1. 两平台的 Runtime 都是"任意框架/语言"的托管容器，严格说任何框架都能两边跑。
2. **官方支持的交集是 Google ADK 体系**：火山侧 veADK 本身构建在 Google ADK 之上（火山官方首推框架）；阿里侧 agentrun-sdk 官方提供 google-adk 集成扩展。
3. **选型建议：用 veADK 开发、部署到 AgentKit**（已拍板的目标平台）。核心 Agent/工具按 Google ADK 范式组织；未来若需迁移或双跑阿里 AgentRun，只需替换平台集成层（模型接入、知识库、部署配置），Agent 业务逻辑可保留。
4. 备选：LangChain/LangGraph（阿里官方集成、火山可部署），但火山侧无官方脚手架，知识库/记忆需自行调 VikingDB API，集成成本高于 veADK。

### 10.3 与本项目已拍板架构的对应关系
| 本项目需求（见九章总体方向 / 9.3） | veADK / AgentKit 对应能力 |
|---|---|
| 单主 Agent + AI 自主决策，不写死流程 | veADK Agent + tools 自动编排（LLM 自主决定调用什么） |
| 业务规则沉淀为技能/skills | AgentKit **skills 机制**（官方 samples 含 150+ skill 与「运行 skills 的智能体」教程，含 HR 招聘类示例） |
| 需要时派子 agent | **sub-Agents** 层级协作（官方 multi_agents 示例）、A2A 协议 |
| 知识库放 AgentKit 平台 | AgentKit Knowledge / VikingDB（官方 RAG 示例 `viking_knowledge`） |
| 后端调用时传 employeeId 等变量 | Runtime API 调用入参 + ADK session state（工具经 ToolContext 读取）——**开发期第一个验证项** |
| 盖亚 7 个 HTTP 接口 | 定义为 function tools，JWT 获取与缓存做在工具层 |
| 最终输出请假单 JSON 给后端 | Agent 结构化输出（output schema） |

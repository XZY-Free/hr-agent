## 一、入口层：消息进来后的五道关

用户消息进入主流程后，按以下顺序处理：

### 1.1 透传数据识别（`_transparent_data_` 前缀）
- 前端表单回填的数据以 `_transparent_data_` 开头注入，内含 JSON（typeName/startDate/endDate/startTime/endTime/reasons）。
- 识别到此前缀 → 直接解析槽位，跳过对话理解，走请假提交。
- 【业务确认】该分支是同事为方便观察入参加的调试节点，业务上可忽略；协议暂保留。
- 【新系统承接】主 Agent prompt 识别前缀 → 解析后转交请假 Agent 直接走提交校验。

### 1.2 空输入拦截
- 空消息 → 回复"你输入的内容为空"。
- 【新系统承接】由模型自然应对，无需专门节点。

### 1.3 转人工判断（问题分类节点，二分类）
判定为【转人工意图】的三个条件（满足其一）：
- **条件A 关键词命中**：人工、客服、人工客服、转人工、投诉、举报、起诉。
- **条件B 直接指令**："转人工"及其口语变体（"我要转人工""帮我转客服"）。
- **条件C 负面情绪**（软触发，不直接转人工，输出安抚话术）：愤怒（骂人/强烈指责/全大写）、失望（绝望/放弃/"没用"/"算了"）、讽刺（反讽）。
- 命中 → 回复引导语"请您回复'转人工'…"。
- 【新系统承接】主 Agent prompt 分发规则第 6 条；话术保留 PHRASES["handoff"] 原文。

### 1.4 核心意图四分类（请假意图判断子应用）
四类：**请假意图 / 取消请假 / 咨询意图 / 其他意图**。严格按优先级 1→2→3→4 判断，**只输出一个标签不解释**。

#### 规则1：请假意图（含一票否决——最关键的业务规则）
**第一步 · 强制排除（一票否决）**——以下任一情况，即使含请假动词也排除出请假意图，归为咨询：
1. 系统异常/反问追问：含疑问词（为什么、为啥、怎么回事）或异常描述（是0、不对、报错、点不了、失败、没数据）。
2. 主观犹豫/情绪宣泄：对是否请假的纠结担忧或情绪表达（不知道批不批、好纠结、敢不敢、太累了、烦）。

**第二步 · 判定条件**（未触发排除时，满足其一）：
1. 显性意图：含动作动词（请假、休、申请、改、换、填）。"时间改成明天""换成病假"算改单请假。
2. 纯时间要素：输入**仅包含**时间/日期，无其他业务词（"明天""下周三""下午""2024-03-01""三天"）。

**无效排除**（不算请假）：
- "我想请假，但是我不知道现在还有没有假" → 触发异常排除 → 咨询。
- "我想请假，但不知道老板批不批" → 触发犹豫排除 → 咨询。
- "年假""去医院""家里有事"（纯类型/理由，无动词） → 咨询或其他。

**示例对比**：
- "明天" → 请假（纯时间）
- "明天年假" → 请假（时间+类型=快捷申请）
- "我想休年假，系统卡了" → 咨询（异常一票否决）
- "有点想请假，怕领导不高兴" → 咨询（情绪一票否决）

#### 规则2：取消请假
- 关键词：取消、撤销、撤回、销假、不请了、不要了。
- 需含上述关键词且通常提及请假/申请/具体假期。
- 【新系统承接】主 Agent 直接回复固定话术 PHRASES["cancel_leave"]，**不进请假流程**。

#### 规则3：咨询意图
- 疑问词：怎么、如何、需要、是否、能否、可以吗、有没有、多久、多少、什么。
- 纯名词询问（仅输入假期类型名无动词）。
- 主题：请假流程、天数、审批状态、余额查询、资格条件。

#### 规则4：其他意图
- 考勤/排班/加班等功能性查询操作关键词：我的排班、考勤统计、加班申请、我的表单、打卡、异常、加班余额。
- 纯理由陈述（无请假动词）。
- 闲聊/问候。

### 1.5 "是否最快捷"代码判断（请假意图进入后）
判定逻辑（代码节点原文）：
- 维护 28 个有效假期名清单（含"调休""年假"两个口语变体）。
- 直接匹配清单 → 标准化（"调休"→"调休假"、"年假"→"年休假"）→ 返回假期名。
- 以"请"开头且去"请"后是有效假期 → 标准化返回。
- 其他 → 返回"非快捷"。
- 返回假期名 → 走快捷路径；返回"非快捷" → 走非快捷 C 线。
- 【新系统承接】**此判断整体删除**——模型直接理解口语假期类型 + 日期，无需二分。快捷/非快捷的 7 个同构子流程全部消失。

## 二、请假域

### 2.1 快捷路径（7 个同构子流程，仅日期偏移不同）
触发：纯时间要素短句（今天/明天/后天/大后天/下周X/昨天/前天 + 请假）。

每个子流程骨架（a1=今天、a2=明天、a3=后天、a4=大后天、a5=下周某日、B=昨天/前天补登）：
1. **文本拼接排班表** → 判断"提前 1 小时下班"特例（是则 typeName=调休假）。
2. **代码计算目标日期**（偏移量是各子流程唯一差异）→ 从排班数据提取当天班次。
3. **首班时间是否 00:00** → 是则休息日/未排班（固定话术："正常休息不用请假"/"还未排班"）。
4. **写 startDate/endDate/startTime/endTime** → 开始>结束则 endDate+1（夜班跨天）。
5. **正则匹配"上半/下半/全天"** → leaveDays = 0.5 / 1 天。
6. **查余额校验 → 组装请假单提交 → 指定回复**。

【新系统承接】7 个子流程合并为请假 Agent 的模型自主处理：理解口语日期 → 调 get_schedule 查证 → 槽位填充 → submit_leave 校验。

### 2.2 非快捷路径（C 线，126 节点，自由文本请假状态机）

#### 入口特判
- 今日"提前 1 小时下班"特例 → 调休假。
- 正则防止一条消息含多种假期（tag 变量标记）。

#### 一级意图分类（qwen-max，四分类）
1. **错误请假申请**（高优先级）：一句话含两个及以上不同假期类型关键字（病假、婚假、产假、陪产假、年假、调休、事假）→ 回复"请分开提交"。判定日期断裂的核心标准是"中间有空缺工作日"。
2. **余额查询** → 转查询假期余额子应用。
3. **改换类型** → 走改单分支。
4. **请假申请** → 走主线。

#### 请假申请主线（信息提取 → 校验 → 提交）
**四要素并行提取**（4 个 contentExtract 节点）：
- **休假类型**（typeName）：预清洗忽略"请""请假"等动词，严格匹配标准假期名清单。
- **日期**（startDate/endDate）：口语日期解析（"下周三"→具体日期），格式 xxxx-xx-xx，默认空。
- **时间**（startTime/endTime）：格式 xx:xx，默认空；结合本周当前时间 cTime 计算。
- **事由与天数**（reasons/leaveDays）：reasons 只提取用户明确表述不推测；leaveDays 如"1.5天""2小时"。

**完整度校验**：缺槽 → 追问话术（一次问一个）；用全局变量记住已收集信息，多轮逐步补齐——这是 20+ 全局变量存在的根本原因。

**时间精修**：
- AI 对话识别时间段/调休 → 真实时间提取 → 年份校验 → 跨天修正。
- glm-4.7 时间分析器：从自由文本提取起止日期范围，无法计算返回"时间为空"。规则优先级：用户明确年/月/日 > 推算 > 默认空。节假日影响：调休工作日按正常日期、法定节假日按节假日。

**排班核算**：
- 调"测试-获取排版信息"子应用查排班（3 段日期范围查询后合并）→ 计算实际天数 leaveDays。
- 调"根据休假类型去判断是否跳过休息日"子应用校正起止日期（见 2.4）。

**提交**：代码节点（入参六元组 typeName/startDate/endDate/holidayType/reasons/leaveDays）→ 组装 leave_support JSON → 回复，tag 归零。

#### 改单分支（二级分类，qwen-plus 四分类）
用户中途修改，先识别改什么：
1. **修改假期类型**：关键词（换成、改为、算作、选错）+ 假期名词。
2. **修改假期日期**：关键词（改天、推迟、提前、延长、缩短）+ 日期词。
3. **修改假期时间**：关键词（几点、晚到、早走、按小时、推迟半小时）+ 时刻词。
4. **修改假期理由**。
- 提取新值 → 汇合到同一提交点。

#### C 线固定话术（answerNode 原文，合规话术保留）
- 多种假期："如需申请多种假期或者不连续时间段，请分开提交申请~这样哆啦可以更好地帮您处理😊"
- 休息日："您的请假时间为正常休息时间，不用请假哦"
- 未排班："您的请假时间还没有排班，请您在排班后再试（哆啦小贴士✨ 排班可以问问您的直接上级领导）"
- 【新系统承接】PHRASES 保留原文（rest_day/not_scheduled），prompt 承担追问措辞。

### 2.3 三道公共安全门（提交前必过）
1. **权限门**：调盖亚 getEmployeeCanApplyLeaveType 查可申请假期类型 → 不在列表 → "你无权申请该假期"。
2. **性别门**（代码节点 leaveGenderMap 原文）：9 类假期限性别——
   - 女（F）：产检假、产假、无薪产假、有薪产假、产前假、哺乳假。
   - 男（M）：无薪侍产假、有薪侍产假、陪产假。
   - 不在表内（如年假、事假）→ 不限性别，视为符合。
   - 逻辑：解析员工信息取 sex 字段；假期在表内则 sex 必须匹配，不匹配 → "不符合"。
3. **余额门**：查该假期剩余额度，不足 → 拒绝。

【新系统承接】`submit_leave` 工具内代码校验链，顺序：`no_permission → gender_mismatch → rest_day/not_scheduled → insufficient_balance → invalid_days`。模型绕不过去。
- **性别校验是条件触发**：仅当 `type_name` 命中 `LEAVE_GENDER_MAP`（9 类限假）才调 `get_employee_info` 查性别；年假等不限性别的假期省一次接口调用。
- **排班查两次**：第一次只查首日判断是否休息日/未排班（早失败省后续调用）；第二次查完整范围供跳休推算校正 `end_date`。

### 2.4 跳休规则（27 类假期映射表——核心业务资产）
作用：根据假期类型决定请假起止日期推算方式（是否跳过休息日）。全部为代码节点，无 LLM、无 HTTP。

**执行流程**：
1. **天数解析**：解析请假时长（"1.5天"→1.5、"X个月"→×30 天）；无法解析或 **> 27 天** → 返回"否"。
2. **分支**：
   - **天数 > 27 或不可解析** → **工作日收缩模式**：startDate 向后找第一个工作日、endDate 向前找最后一个工作日。
   - **天数 ≤ 27** → 提取 typeName → 查 27 类映射表：
     - 标记"否"（跳过休息日）→ 以排班表为准，从 startDate 起跳过休息日（shiftCode 为 OFF / off_day / defaultOFF 开头）逐日数够 N 个工作日，endDate = 最后一个工作日；startDate 不在排班数据内 → 按自然日加 N-1 天。
     - 标记"是"或未收录 → 连续自然日计算，endDate = startDate + (N-1) 天。

**27 类映射表**（见《迁移梳理报告》§3.7，已落 constants/leave_rules.py，逐字一致）：
- 连续计算（是，13 类）：婚假、产假、病假、育儿假、计划生育假、无薪产假、有薪产假、子女护理假、不定时员工日常休假、产前假、陪产假、出差、公出。
- 跳过休息日（否，14 类）：丧假、产检假、非独生子女护理假、事假、调休假、无薪侍产假、80%病假、调休假(综合工时)、有薪侍产假、年休假、无薪假、路程假、全薪病假、哺乳假。

【新系统承接】`calc_end_date` 纯函数 + `SKIP_RESTDAY_MAP` 常量，算法逐行移植，含 >27 天收缩、按排班 OFF 跳休、自然日连续三路径。该函数不作为独立工具挂载，由 `submit_leave` 校验链末步调用（确定性规则强制执行，模型绕不过去）。

### 2.5 请假单组装与提交
代码节点组装 JSON（字段：businessType=leave_support、typeCode、typeName、startDate、startTime、endDate、endTime、reasons、leaveDays）。typeCode 来自 27 类 HOLIDAY_TYPE_CODE 映射（如年休假=A31、婚假=A03、陪产假=A08）。

**【业务确认】旧系统不真正提交**——组装后吐给后端，后端调盖亚提交接口。
【新系统承接】变化点：智能体将来自己调提交接口（`submit_leave` 工具），用自然语言告知结果。一期干跑（校验全跑、提交打日志、返回模拟成功）——**干跑本身就是 mock，业务确认先用 mock 无限期替代**；接口到位后仅需实现 `_do_submit` 替换干跑，不动校验链。

## 三、咨询域（人力AI咨询新，90 节点）

管线：**名词解释 → 问题改写 → 非人力过滤 → 业务分类 →（咨询知识库 / 地区育儿假 / 考勤计算）→ 专家回答 + 追问生成**。

### 3.1 名词解释（qwen-plus）
- 任务：严格按"标准术语定义库"提取用户输入的核心名词并输出标准解释。
- 规则：词汇拆分独立比对（不组合）；部分匹配即输出；全未匹配则不输出；纯净输出无思考过程。
- 术语库含：公出、公出用车、出差、因公出差、其他公出、流产假、产检假、产前假、陪产假等定义。
- 【新系统承接】并入咨询 Agent 单次对话，模型自主理解术语，不再是独立节点。

### 3.2 问题改写（qwen-plus，history=3）
- 角色："意图补全与文本替换工具"，**绝对不是问答机器人**，只输出改写后的问题文本。
- 两步：意图补全（指代消解）+ 语义词汇替换（口语→标准术语，如"饭钱"→"膳食补贴"）。
- **首轮绝对禁止补全**：无聊天记录时只做术语替换，原样输出。
- 严格条件补全：有聊天记录 + 问题缺信息明显依赖记录 + 同一话题逻辑 + 单一明确主体。
- 【新系统承接】咨询 Agent prompt 承担，模型自主改写。

### 3.3 非人力过滤（两步：关键词检索 + 语义比较）
**第一步**：知识库检索"非人力关键词"（相似度阈值 0.17）。
**第二步**（qwen-plus，history=6，语义比较）：判断用户问题与非人力关键词是否同核心业务含义。
- 警惕"字面陷阱"：补卡（考勤）≠ 饭卡补办（行政）；个人劳动合同查询（人力）≠ 合同管理系统操作（非人力）。
- 遍历关键词数组，任一与问题核心诉求一致 → "非人力"；全不符合或字面相似诉求不同 → "人力"；数组空 → "人力"。
- 非人力 → "建议您咨询其他企业部门"。
- 【新系统承接】咨询 Agent prompt 承担过滤，**非人力关键词库不上传**（已确认）。

### 3.4 业务分类（qwen-max，多分类）
分类后走不同支线：
1. **咨询知识库**（兜底）：事务性/操作性/规则类问题。"怎么做""在哪操作""能不能""是否允许""需审批吗""公司规定""流程""扣不扣钱（非数值）"。即使提"育儿假"但问申请方式/审批/材料 → 仍归此类。
2. **地区育儿假时长**（严格限定，须同时满足三条件）：精确含"育儿假"三字 + 明确提及具体地区 + 仅问天数/时间。无地区/问流程/问个人余额/用"陪产假"等替代词 → 不属此类。
3. **计算类** → 考勤智能分类（迟到早退/年假/医疗假/育儿假/咨询类）。
4. **兜底** → AI 寒暄（火山方舟 ep-20241225182328-2pz7p）。

### 3.5 各支线检索与回答
- **咨询知识库**：代码判断"正常制度" → 正常则多路检索（系统操作手册 + 知识库搜索#8 + 知识库搜索#10）合并 → qwen3-max 专家回答；否则知识库搜索#11 → qwen3-max 另版 prompt。
- **地区育儿假**：AI 提取省份 → 知识库搜索#8（**阈值 1.0 精确匹配**）→ 代码格式化 → 回复。

### 3.6 专家回答 prompt 要点（qwen3-max / qwen3.7-max）
- 角色：资深人力资源管理专家，专业度与亲和力并重。
- 核心原则：精准克制（仅回复强相关，绝不冗余）、全局视角（分对象/类型差异化规定按需提供）、视觉友好（结构化排版）、严谨合规（严格依知识库，不推理不发散）。
- **内容红线**：对"当地政策"等限定性条款绝对敏感，绝不遗漏"当地有特殊规定的，从其规定""除当地政府特别规定外"等表述。
- 禁止：主动解释原因/影响/示例/后续步骤/关联政策、复制大段原文、提供过度细节、创造不确定性。
- 禁止：向用户说明引用了哪个制度/手册、说明输出格式。
- 必须一个问题一个答案；多问题则每个都答。
- 【新系统承接】咨询 Agent prompt 承担，保留上述红线约束。

### 3.7 追问生成（qwen-max，生成追问#27）
- 唯一任务：根据原问题主题 + 知识库内容，生成 **1 个**追问。
- 禁止礼貌用语（请、您好、谢谢、能否、麻烦您、请问）。
- 禁止过渡句（"为了更好地回答""根据知识库显示"）。
- 禁止推测引申（不得用"一般""通常""可能""建议"）。
- 必须基于知识库**实际存在**的政策点，禁止编造。
- 必须是知识库中**已有明确答案**的问题，禁止要求用户提供信息（"你所在地区""你的工龄"）。
- 策略：优先同题延伸（原问资格，追问计算方式/限制条件/例外情况）。
- 【新系统承接】咨询 Agent prompt 要求回复末尾自然附 1-2 个相关问题，不做结构化字段。

## 四、查询域（盖亚 API 工具集）

统一两段式模式：**HTTP 获取盖亚 JWT → 代码解析 JWT（取 data 字段作 Bearer token）→ HTTP 调业务接口 → 代码解析响应 → 格式化话术**。失败/异常均有 catch 分支。

### 4.1 认证（所有接口前置）
- POST `/identity/api/v1/oauth`（form：grant_type/corp_id/client_secret）。
- 响应 `{"result":true,"code":200,"data":"<JWT>"}`，data 即 JWT。
- 旧系统每次调用都重新 oauth。
- 【新系统承接】gaia_client 按有效期缓存 JWT（25 分钟 TTL），30s 超时 + 1 次重试（提交类除外）。

### 4.2 六个业务接口
| 接口 | 用途 | 环境 |
|---|---|---|
| getemployeeleaveremaindata | 假期余额（按类型过滤） | prod |
| getEmployeeCanApplyLeaveType | 可申请假期类型（权限） | **sandbox** |
| medical/period/info/get | 医疗期 | prod |
| person/search-effective | 员工在职信息（工龄） | prod |
| getScheduleData | 排班数据 | **sandbox** |
| （请假提交） | 一期干跑 | — |

环境混用、排班 tenant 硬编码 `snowbeertest`、Apifox 残留头——【业务确认先按导出原样】。

### 4.3 响应解析（代码节点原文依据的字段）
- **假期余额**：`details.employeeData[0].employeeDetailData[]`，每项 effectiveYear/leaveCode/leaveName/leaveUsed/leaveTotal/leaveRemain。
- **假期权限**：`data[]`，每项 LeaveCode/LeaveType。
- **医疗期**：`details[]`，每项 quota/used/balance。
- **员工信息**：`details[]`，取 sex、socialService（形如"6 年 4 月 0 天"按空格 split）。
- **排班**：`details.employeeData[0].employeeDetailData[]`，每项 shiftDate/shiftCode/shiftName/startTime/endTime；shiftName 为 null 视为无效班次。

### 4.4 年假折算（独立业务逻辑）
1. 查员工信息 → 解析工龄（参工年限 socialServiceYear）。
2. 档位：<10 年 → 5 天；≥10 年 → 10 天。
3. **恰在满 10 年的跨档年** → 按参工纪念日（月/日）分段折算：
   - 前段（1月1日 到 入职日含）：`leaveBefore = floor(daysBefore/totalDays × 5 × 10)/10`（按 5 天折算）。
   - 后段（入职日次日 到 12月31日）：`leaveAfter = floor(daysAfter/totalDays × 10 × 10)/10`（按 10 天折算）。
   - 闰年 366 天；floor 后 toFixed(1) 保留一位小数。
   - 示例：11月3日/2025 → daysBefore=307 → before=4.2；daysAfter=58 → after=1.5。
4. 再查年假余额 → 话术"X月X日前年休假按 N 天折算…"。
- 【新系统承接】`split_year_quota` 纯函数逐行移植，**禁止优化舍入方式**；`calc_annual_leave` 工具组合员工信息+折算+余额（组合工具，模型主动决定何时查年假）。

## 八、验收检查点（按业务规则）

评测时拿这些"预期行为"对照：

1. "我要请年假和事假" → 拒绝，要求分开提交（C 线错误请假申请检测）。
2. "请假会扣钱吗" → 走咨询，不发起请假（一票否决）。
3. "我想休年假，系统卡了" → 咨询（异常一票否决）。
4. 请休息日的假 → "正常休息不用请假"，不出请假单。
5. 女员工请陪产假 → 拒绝（性别门）。
6. 无权限假期 → "你无权申请该假期"（权限门）。
7. 余额不足 → 拒绝（余额门）。
8. 周五开始请 3 天年假 vs 3 天婚假 → 结束日期不同（跳休 vs 连续）。
9. "育儿假有几天"没说省份 → 先追问省份。
10. 问迟到扣款 → 引用制度原文数字，不编造。
11. "打开打卡明细" → 回复末尾带 `[[JUMP:punch-details]]`。
12. "转人工" → 回复转人工引导话术。
13. "取消明天的请假" → 回复固定取消话术，不进请假流程。
14. "明天" → 走请假（纯时间要素）。
15. "年假" → 走咨询（纯类型无动词）。
